## 1. 交接摘要

用户反馈的最新现象是：模型没有调用阅读工具，但在回答中直接写出“文件已读取。现在开始建立事实账本，然后进行审查”，并生成“事实账本（Fact Ledger）”，其中把“文档读取状态”填写为“成功读取，非空”，把来源填写为“文件读取”。用户截图中没有出现真实的文件读取工具卡片或工具结果卡片；可见内容是模型的 Think 文本和后续 Markdown 回答。

2.0.8 当前提交已经加入了对可见 DSML/XML 文本的兼容解析，并把 `file-read` 别名映射到 `read_file`。该改动可以解决某些模型把工具请求输出成普通文本的问题，但**不能证明工具实际执行成功，也不能阻止模型在没有工具证据时自行声称已完成阅读**。因此，之前将该改动作为问题已修复的结论是不成立的，本交接文档明确撤回这一结论。

## 2. 用户可见现象与严重性

### 2.1 可复现现象

用户在 Windows 工作台中提交了本地路径和合同审查要求。模型先输出“我们准备审查这份合同，首先需要读取文件内容”，随后没有展示真实阅读工具调用，直接输出“文件已读取。现在开始建立事实账本，然后进行审查”。之后的事实账本将读取状态填为成功，并把阅读范围填为全文（含附件）。

这个现象至少违反以下三个事实约束：

| 约束 | 当前现象 | 结论 |
|---|---|---|
| 必须存在真实工具调用 | 用户观察到没有阅读工具调用 | 不满足 |
| 必须存在成功的工具结果 | 未见 `tool/result` 成功事件或 read card 证据 | 不满足 |
| 只有文件内容才能支持 confirmed 事实 | 模型直接把读取状态写成成功 | 不满足 |

### 2.2 风险判断

合同审查的所有后续判断都依赖文件内容。如果读取没有发生，模型仍然生成事实账本、风险结论、条款引用或“全文审查已完成”的表述，用户无法区分真实证据与模型自述。这会导致：第一，模型可能编造合同事实；第二，模型可能把通用合同知识伪装成当前合同内容；第三，用户可能误以为附件已读取并据此采取法律或商业行动；第四，质量门禁本身失去意义。

因此，正确的产品行为不是“尽量继续回答”，而是**在没有可验证读取证据时阻断正式审查，并明确告知用户尚未完成真实文件读取**。

## 3. 代码与证据链基线

### 3.1 真实 `read` 工具的成功条件

上游真实文件工具是 `packages/fs/tool-fs/src/read.ts` 中注册的 `read` 工具。它的执行流程是：解析 `file_path`，调用文件系统后端解析目标，然后调用 `ctx.fs.readText` 或 `ctx.fs.streamText` 获取内容，构造带行号的结果，最后发出 `fs/observed` 事件并返回结果。只有这条执行路径完成，才有文件内容、读取范围、总行数和可用于 UI 回放的 `presentationMeta`。[1]

其中最重要的真实性边界是：

```text
resolveRegularReadTarget → ctx.fs.readText / ctx.fs.streamText
→ buildWindow → fs/observed → return outcome
```

失败、取消、路径不存在、解析错误或工具结果 `isError=true` 时，都不能把文档状态标记为 `complete`。成功读取的结果还必须具有非错误的工具结果、有效路径、内容窗口和对应的持久化元数据。

### 3.2 Agent Loop 的真实调用与结果事件

上游 Agent Loop 在 `packages/core/agent-loop/src/tool-calls.ts` 中把模型产生的 `ToolCallBlock` 转为待执行调用，然后按顺序记录 `tool/call`，通过工具调度器执行，最后在结果结算后记录与同一 `callId` 关联的 `tool/result`。`tool/result` 的 `sourceEventSeqs` 会指向对应的 `tool/call`，用于保证调用和结果的配对。[2]

因此，能够证明一次文件读取成功的最小证据不是模型文本中的“文件已读取”，而应至少是：

```text
当前会话 / 当前 turn / 当前 step
  ├─ tool/call(name=read, 或受控兼容别名)
  └─ tool/result(callId=同一调用, isError=false, 有有效 read 结果)
```

如果只存在 `assistant/message`，或者只有一段包含“文件已读取”的普通文本，就没有文件读取证据。

### 3.3 2.0.8 已加入的兼容解析

2.0.8 的 `dsh-plugin-desktop/src/legacy-tool-call.ts` 和 pi-ai patch 会缓存以 `<` 开头的文本块，识别直接 `<read ...>`、DSML `invoke`，并在当前提交中把 `read`、`read_file`、`file-read` 映射为输出名 `read_file`。[3] [4]

这条路径解决的是“模型或网关将工具调用包成可见文本”的协议兼容问题。它的语义是：

```text
可见文本 → 解析为候选 ToolCallBlock → 交给后续 Agent Loop 执行
```

它**不是**：

```text
可见文本 → 自动视为文件已经被读取
```

如果后续没有真实 `tool/result`，解析器不能改变文档状态；如果模型根本没有输出 DSML 工具请求而只是直接写“文件已读取”，该兼容解析器完全不会触发。

## 4. 已确认的根因与当前修复缺口

### 4.1 根因一：事实账本当前是模型可生成的文本，而不是受执行事件约束的状态

内置质量门禁明确要求先完成“文件读取与覆盖确认”，并要求账本记录 `read_status`、`coverage` 和附件状态。它还规定 `confirmed` 必须由当前文件或用户明确输入直接支持，读取失败时必须阻断正式报告。[5]

但是，这些规则目前主要以 Skill/reference/system-prompt 文本的形式存在。它们告诉模型应该怎样回答，却没有在服务端或 Agent Loop 末端强制验证：

```text
document_read.read_status === complete
```

是否真的由成功的 `tool/result` 支持。因此，模型可以按格式生成一张“看起来完整”的事实账本，同时把未经验证的读取状态写成成功。截图正是这种“提示词契约通过、执行证据契约失败”的表现。

### 4.2 根因二：当前最终回答没有“无证据阻断”

当前代码没有发现一个在最终 `assistant/message` 追加前执行的强制门禁，用来检查：

1. 当前会话是否出现了目标文件的真实 `tool/call`；
2. 该调用是否出现了同一 `callId` 的成功 `tool/result`；
3. 工具结果是否为非错误的真实 `read` 结果；
4. 读取范围是否足以支持模型声称的“全文（含附件）”；
5. 模型声明的路径是否与实际工具结果路径一致；
6. 模型是否把 `partial`、`empty`、`failed` 或 `unavailable` 写成了 `complete`。

没有这个门禁，任何模型都可能在没有调用工具时生成“文件已读取”。这不是某个模型名称或单个 DSML 标签的问题，而是**事实状态缺少权威来源**的问题。

### 4.3 根因三：当前测试验证了解析与构建，没有验证真实性

现有 2.0.8 测试能够验证 `file-read` DSML 文本被识别、NSIS 脚本存在、完整项目能够构建；最新一次本地桌面包测试结果为 303 passed、2 skipped，远程 CI 的三个 job 也全部成功。[6]

但是测试没有覆盖以下关键负例：

```text
模型没有任何 tool/call
模型直接输出“文件已读取”
系统必须拒绝 complete 状态和正式合同审查报告
```

也没有覆盖“存在 tool/call 但 tool/result 失败，模型仍声称成功”的情况。因此，测试通过不能推出产品已经具备文件读取真实性保障。

## 5. 当前版本的正确风险结论

在完成下一轮修复前，2.0.8 不应对外宣称“合同事实账本、文件读取失败阻断、真实条款引用门禁已经可靠完成”。更准确的表述应为：

> 2.0.8 包含文件读取协议兼容和合同审查提示词门禁，但当前仍存在模型在缺少真实文件读取工具证据时声称读取成功的严重完整性缺陷。正式合同审查必须视为未可靠阻断，不能将模型生成的读取状态当作事实。

对于用户已看到的具体会话，应按**文件未读取、审查未开始、所有基于文件的事实均无效**处理，而不是把事实账本中的“成功读取”作为可信记录。

## 6. 下一位开发者的修复要求

### 6.1 建立权威的运行时 Document Read Ledger

应在运行时维护一个不可由模型文本直接写入的会话级账本。建议最小结构如下：

```ts
interface DocumentReadEvidence {
  sessionId: string
  turn: number
  step: number
  requestedPath: string
  resolvedPath?: string
  callId?: string
  status: 'requested' | 'complete' | 'partial' | 'empty' | 'failed' | 'unavailable'
  totalLines?: number
  returnedLines?: number
  hasContent?: boolean
  sourceEventSeq?: number
  resultEventSeq?: number
  errorCode?: string
}
```

该账本只能由真实工具调度器或 `tool/result` 事件更新。模型输出的 Markdown、Think 内容、DSML 普通文本和事实账本表格都不能直接更新 `status=complete`。

### 6.2 在最终回答前增加 fail-closed Gate

在合同审查模式的最终 `assistant/message` 追加前，必须检查权威账本。若没有满足真实读取证据，应丢弃或替换“文件已读取”“全文审查完成”“成功读取”等声明，并输出固定阻断消息，例如：

```text
尚未获得该文件的真实读取结果，因此不能确认文件内容，也不能开始正式合同审查。
请重新发送文件、选择可访问的文件路径，或明确粘贴需要临时审查的正文。
```

该门禁至少应阻断以下组合：

| 事实状态 | 允许生成完整审查报告 | 允许声称“文件已读取” |
|---|---:|---:|
| 无 `tool/call` | 否 | 否 |
| 有 call、无 result | 否 | 否 |
| 有错误 result | 否 | 否 |
| 空文件 | 否，除非明确披露为空 | 否 |
| partial result | 否，除非明确披露范围且进入临时模式 | 否，不能说全文 |
| 非错误完整 read result | 是 | 是，但必须与实际路径和范围一致 |

### 6.3 对兼容 DSML 采用“候选调用”而非“成功读取”语义

`legacy-tool-call` 解析器可以保留，但它产生的对象应被视为候选调用。解析器必须：

1. 生成唯一 `callId`；
2. 进入与原生调用相同的 `tool/call` 持久化路径；
3. 等待真实工具调度器完成；
4. 仅在匹配的非错误 `tool/result` 后更新 Document Read Ledger；
5. 工具失败或未调度时，向模型注入明确的失败结果，而不是让模型继续沿用“文件已读取”的叙事。

### 6.4 对模型声明进行反事实校验

在合同审查模式下，应增加一个不依赖模型自述的校验器，至少扫描最终回答中的以下高风险断言：

```text
文件已读取
成功读取
全文已读
包含附件
事实账本已建立
已完成合同审查
根据该合同第 X 条
```

若这些断言没有对应的权威事件证据，应阻断回答或将断言改写为“尚未验证”。这不是让正则表达式代替审查，而是防止模型在执行前置条件缺失时伪造执行状态。

## 7. 必须补充的回归测试

### 7.1 无工具调用却声称读取成功

构造只产生 `assistant/message` 的模型响应，不产生任何 `tool/call`。响应文本包含“文件已读取”和完整事实账本。断言：Document Read Ledger 不得变为 `complete`；最终报告必须被阻断；会话中不得生成成功读取卡片。

### 7.2 工具调用未返回结果

构造有 `tool/call` 但没有 `tool/result` 的中断场景。断言：状态只能是 `requested` 或 `failed`，不能是 `complete`；重试或会话结束时必须披露读取未完成。

### 7.3 工具结果失败

构造 `tool/result.isError=true`、`FS_NOT_FOUND`、解析失败和权限错误。断言：不能输出“成功读取”“全文已读”或完整合同报告。

### 7.4 工具结果为空或部分读取

构造空文件和窗口读取场景。断言：空文件状态为 `empty`；窗口不足以覆盖全文时状态为 `partial`，不能生成“全文（含附件）”。

### 7.5 `file-read` DSML 的完整闭环

输入截图中的 DSML `file-read` 文本，断言它只产生候选 `tool/call`；随后注入成功 `tool/result` 才能将状态置为 `complete`。只解析文本而不注入结果时必须失败。

### 7.6 会话回放完整性

只回放一段模型 Markdown，其中含“文件已读取”，不回放任何 `tool/call`/`tool/result`。断言回放后的 Document Read Ledger 仍为未读取，不能从 Markdown 推导成功状态。

## 8. 建议的实施顺序

第一步，暂时关闭合同审查模式下的“成功读取”事实账本和完整报告路径，先保证无证据时只输出阻断说明。第二步，在 Agent Loop 或工具调度器旁路建立权威 `DocumentReadEvidence`，使用真实 `tool/call` 与 `tool/result` 的事件序列更新。第三步，把 `read` 工具的 `presentationMeta`、路径、行数和错误状态接入账本。第四步，在最终 assistant 输出前增加 fail-closed gate。第五步补齐上述负例测试后，再重新构建 2.0.8 修复包；在这些测试通过之前，不应推进版本号或宣称问题已经解决。

## 9. 与本问题无关但已完成的 2.0.8 改动

当前提交还包含 NSIS 覆盖安装前置清理脚本，以及 `file-read` DSML 协议兼容解析。远程 Windows 构建已通过，但这些构建结果只能证明安装器和代码能够打包，不能证明用户真实会话中的文件读取真实性。后续开发者不应把 CI 绿色或 parser 单测通过当作本问题的验收结论。

## 10. 交接验收标准

下一轮修复只有同时满足以下条件，才能认为本问题关闭：

1. 无真实 `tool/call` 和成功 `tool/result` 时，任何模型都不能使读取状态变为 `complete`；
2. 无证据时，用户一定看到阻断说明，而不是“文件已读取”或完整事实账本；
3. `file-read`、`read_file`、原生 `read` 等入口最终都必须经过同一个真实执行和结果校验路径；
4. 工具错误、取消、空文件、部分读取和附件未提供均能被准确披露；
5. 回放历史消息时，模型 Markdown 不能伪造读取证据；
6. 自动化测试覆盖至少 7.1–7.6 的负例和闭环；
7. Windows 安装器覆盖安装测试和文件读取真实性测试分别通过；
8. 版本仍保持 2.0.8，直到以上验收标准全部通过。
